# External Adversary AI Assessment

## Purpose

This extension addresses the most common operational case: an external threat actor uses AI outside the victim organization's environment. The defender usually cannot observe the attacker's model, prompts, orchestration layer, account, or inference logs. Assessment must therefore rely on observable effects inside the organization, external infrastructure evidence, threat-intelligence corroboration, and explicit consideration of alternative explanations.

The objective is not to prove that a particular text or script was generated by AI. It is to estimate whether AI materially supported the external actor's preparation, execution, adaptation, or scaling of the intrusion.

## Visibility Boundary

For an external attacker, the organization may observe:

- Inbound traffic, exploit attempts, payloads, authentication activity, and command-and-control behavior.
- Changes in payloads or tactics following errors, blocking, version disclosure, or defensive action.
- Phishing messages, synthetic media, identity artifacts, and victim-specific interactions.
- Malware, scripts, configuration files, logs, and state artifacts left on compromised systems.
- Public reporting, provider disruption reports, law-enforcement reporting, and shared intelligence.

The organization will usually not observe:

- The attacker's prompts or complete conversation history.
- The attacker's model endpoint, API key, local model, or agent framework.
- Human approval points inside the attack workflow.
- Whether a model generated an artifact, revised human-written content, or merely provided advice.

The absence of internal AI-service telemetry must therefore not be interpreted as evidence that the external actor did not use AI.

## External Adversary Evidence Dimensions

### 1. Adaptive Behavior

Assess whether the actor changes behavior in a context-sensitive manner after receiving feedback from the target.

Examples:

- Revising an exploit after a version banner, stack trace, or application error.
- Selecting a different privilege-escalation or persistence method after a failed attempt.
- Rewriting commands to match the discovered operating system, language, shell, identity provider, or security control.
- Changing a phishing narrative after the victim responds or challenges the sender.
- Reprioritizing systems after discovering trust relationships, administrative roles, or business-critical data.

Adaptive behavior supports an AI-use hypothesis only when the change is semantically related to the feedback. Conventional automation, operator skill, playbooks, and team collaboration remain alternative explanations.

### 2. Dynamic Operational Artifacts

Assess whether the actor produces multiple target-specific or feedback-driven artifacts during the incident.

Examples:

- Payloads that change after failed execution while preserving the operational objective.
- Scripts generated for a specific host, software version, directory structure, or defensive product.
- High-volume spear-phishing variants tailored to individual roles and languages.
- Rapidly refreshed web pages, domains, documents, or social-engineering personas.
- Runtime-generated code or obfuscation that reduces stable static indicators.

Investigators should compare semantic function, control flow, timing, and target context rather than relying only on file hashes or textual similarity.

### 3. AI-Enabled Decision Cycle

Look for a repeated external operational pattern:

```text
Target observation
-> context interpretation
-> new plan or artifact
-> execution
-> defensive or technical feedback
-> revised action
```

A single adjustment is weak evidence. Repeated, rapid, contextually appropriate cycles across several stages or targets provide stronger behavioral evidence of AI augmentation or orchestration.

### 4. Operational Tempo and Scale

Measure whether the actor's observable throughput is inconsistent with known historical tradecraft or a plausible human-only workflow.

Suggested measures:

- Time from error or block to a technically relevant new attempt.
- Number of functionally distinct payload variants per hour.
- Number of targets receiving individualized content.
- Parallel attack paths maintained without obvious loss of context.
- Time from initial discovery to exploitation, privilege escalation, collection, or exfiltration.
- Rate of code, infrastructure, or persona refresh.

Tempo is supporting evidence, not proof. Botnets, large teams, precomputed variants, and established automation can generate similar patterns.

### 5. External Intelligence Corroboration

CTI should determine whether trusted sources have independently reported AI use by the actor, malware family, infrastructure cluster, or campaign.

Corroboration may include:

- Model-provider disruption and misuse reports.
- Vendor or national CERT reporting based on incident-response evidence.
- Law-enforcement or judicial records.
- Malware analysis identifying runtime model access or agentic orchestration.
- Repeated observations from independent organizations.

Actor-level reporting raises prior probability but does not prove AI use in the specific incident under investigation.

## External Adversary AI Confidence Matrix

Score each dimension from 0 to 100:

```text
EAAI = 0.30(Adaptive Behavior)
     + 0.25(Dynamic Artifacts)
     + 0.20(Operational Tempo)
     + 0.15(Intelligence Corroboration)
     + 0.10(Direct Technical Indicators)
```

| Score | Assessment |
|---:|---|
| 0-19 | No meaningful evidence |
| 20-39 | Possible external AI assistance |
| 40-59 | Probable external AI assistance |
| 60-79 | Highly probable external AI involvement |
| 80-100 | Near-confirmed or confirmed, subject to direct-evidence requirements |

A score of 80 or more does not independently establish confirmation. Confirmation requires provider-side evidence, captured attacker infrastructure, recovered prompts or agent state, malware that directly invokes a model, or equivalent direct evidence.

## External Adversary AI Maturity

| Level | Description |
|---:|---|
| AI-0 | No observable AI use. |
| AI-1 | AI supports research, translation, content, or code drafting before execution. |
| AI-2 | AI accelerates attack preparation, targeting, infrastructure, or malware development. |
| AI-3 | AI supports live execution, troubleshooting, discovery, or post-compromise analysis. |
| AI-4 | Agentic workflows select tools, evaluate results, and coordinate multiple attack stages. |
| AI-5 | A highly autonomous system conducts most of the campaign with limited human intervention. |

## Collection Requirements

Organizations should preserve data that allows retrospective behavioral reconstruction:

- High-resolution timestamps across web, WAF, EDR, identity, DNS, proxy, email, and cloud logs.
- Complete HTTP status, error, and response metadata where legally permitted.
- Payload samples from successive attempts, not only the first detected sample.
- Email-thread progression, response timing, and changes in social-engineering content.
- Process, script, file, and command timelines on compromised systems.
- C2 tasking and response artifacts recovered from memory or disk.
- Threat-intelligence reporting with source reliability and information credibility ratings.

## Analytic Questions

1. What target feedback was available to the actor before the behavior changed?
2. Was the next action semantically appropriate to that feedback?
3. Could a deterministic rule or known playbook explain the transition?
4. Did similar adaptive cycles occur repeatedly?
5. Did the actor sustain parallel context-sensitive operations at unusual scale?
6. Is there independent reporting of AI use by the same actor or tooling?
7. What direct evidence would be required to raise the conclusion to confirmed?

## Reporting Language

Preferred wording:

> We assess with moderate confidence that the external threat actor used AI to support live troubleshooting and payload adaptation. The assessment is based on repeated, rapid, and semantically relevant changes following target-generated errors, together with independent intelligence reporting of AI-assisted tooling by the actor. We did not observe the attacker's model, prompts, or orchestration infrastructure, and conventional automation remains a plausible alternative explanation.

Avoid categorical language based solely on polished text, code style, speed, or payload variability.
